How to Audit a Large Language Model: Methodology

You cannot audit what you cannot repeat. That is the first principle, and most LLM audit efforts violate it before they begin — testing a model through a chat interface, recording impressions, and calling the result an assessment. A real audit produces evidence: what was tested, on what data, with what method, by whom, and what was not tested. Everything else is a demo.

6 MIN READ · AIMODELAUDITS.COM · OCTOBER 2026

"An LLM audit is not a grade. It is a sworn statement about what was tested, on what data, by whom — and what wasn't." The methodology below is structured around the dimensions regulators, standards bodies, and serious enterprise buyers actually examine: bias and fairness, robustness, data lineage, benchmark evaluation, and red-teaming. It maps to the NIST AI Risk Management Framework's Measure function and the control objectives of ISO/IEC 42001.

Scope and Threat Model: Before Any Testing

Every audit begins with two documents. The first is the scope statement: which model version, which deployment configuration, which use cases. A model is not a single artifact — GPT-4 with system prompt A in a customer-support deployment is a different audit target than the same weights with system prompt B in a code-review deployment. Version-pin everything: model checkpoint, system prompt, temperature and sampling parameters, retrieval configuration, tool integrations. If the deployment changes, the audit's validity changes with it.

The second is the threat model: what harms are in scope. For a hiring-screening LLM, the threat model centers on discrimination across protected characteristics. For a medical-information LLM, on confabulated clinical guidance. For a customer-facing agent with tool access, on prompt injection and unauthorized actions. The threat model determines which tests matter; testing everything equally is how audits produce hundred-page reports that answer nothing.

The Five Audit Dimensions

1. Bias and fairness testing. Run structured evaluations across demographic dimensions relevant to the deployment. Established instruments include BBQ (Bias Benchmark for QA), which measures stereotyped versus anti-stereotyped response patterns across nine social dimensions, and BOLD, which measures sentiment and regard across demographic prompts. The audit question is not "is the model biased" — every model trained on human text carries bias. The question is whether bias manifests in the deployment's decisions at rates that violate the deployer's stated fairness criteria or applicable law. For consequential decisions — hiring, lending, admissions — this dimension maps directly to Colorado AI Act impact assessment requirements and EU AI Act data-governance obligations. Document the metric, the threshold, and the result. "Tested for gender bias in resume screening; disparate impact ratio 0.94 against a 0.80 threshold; pass" is an audit finding. "Seems fair" is not.

2. Robustness and adversarial evaluation. Test the model against inputs designed to break it: jailbreak prompts, prompt-injection payloads, edge-case formatting, adversarial paraphrases of refused requests. Track attack success rate by category. For agentic deployments, test tool-use boundaries — can the model be induced to take unauthorized actions, leak system instructions, or execute commands outside its scope? Robustness testing is where the EU AI Act's systemic-risk requirements for GPAI models (adversarial testing, red-teaming for models above 10²⁵ FLOPs) and the evaluation practices of frontier labs converge. The audit should report not just pass rates but the specific attack classes tested, because a model robust against last year's jailbreaks may be fragile against this year's.

3. Data lineage and provenance. Document what the model was trained on, what it was fine-tuned on, and what it retrieves at inference time. For foundation models, this means the provider's training-data summary — required under the EU AI Act's GPAI obligations since August 2025. For fine-tuned and RAG deployments, it means the actual datasets: sources, collection dates, consent basis, known limitations. Data lineage is the least glamorous dimension and the one most audits skip. It is also the dimension regulators ask about first, because training-data decisions are where discrimination and copyright exposure originate.

4. Benchmark evaluation. Run standardized capability and safety benchmarks and report scores with confidence intervals, not point estimates. The core instruments: MMLU for broad knowledge, HELM (Stanford's Holistic Evaluation of Language Models) for multi-dimensional assessment, TruthfulQA for confabulation tendency, and domain-specific suites (SWE-bench for code, MedQA for clinical knowledge) matched to the deployment. Use EleutherAI's lm-evaluation-harness or equivalent open tooling so results are reproducible by a third party. Benchmarks don't prove safety — they establish a capability baseline against which behavioral claims can be checked. A model scoring 92% on MMLU that confabulates citations in production has a deployment problem, not a capability problem, and the audit should say so.

5. Red-teaming. Structured adversarial probing by humans, distinct from automated robustness testing. Effective red teams combine domain experts (who know what harmful outputs look like in context) with adversarial generalists (who know how to elicit them). Scope the engagement: number of person-hours, target harm categories, access level granted. Report findings as discrete vulnerabilities with severity ratings and reproduction steps — the format security teams already understand from penetration testing. The EU AI Act requires adversarial testing for systemic-risk GPAI models; Colorado's framework treats adversarial testing as evidence of reasonable care. Red-teaming is becoming the audit artifact with the clearest legal value.

The Evidence Pack

The audit's output is an evidence pack, not a score. Minimum contents: scope statement and version pins; threat model; test plan mapped to dimensions; raw results with methodology notes; findings with severity ratings; limitations — what was not tested and why; and a re-audit trigger list (model version change, prompt change, new deployment context, elapsed time). ISO/IEC 42001's continual-improvement clause and the NIST AI RMF's Manage function both require that auditing be a lifecycle activity, not a one-time event. An audit with no expiration date is a snapshot pretending to be a guarantee.

The organizations doing this well in 2026 treat LLM audits the way mature companies treat financial audits: scheduled, scoped, independently executed, and filed where regulators and boards can find them. The ones doing it poorly are still testing through the chat interface. The December 2027 EU deadline will sort the two groups definitively.
